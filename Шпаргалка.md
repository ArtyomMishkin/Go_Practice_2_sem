# Что мы узнали

Что я понял пока читал методички(основа для ответов на практики)

## Как связаны практики

1. Два HTTP-сервиса (пользователи, заказы) — границы и вызовы по сети.
2. gRPC — другой протокол и контракт в `.proto`.
3. Логи и метрики — что происходит внутри сервиса.
4. Безопасность — шифрование, SQL, атаки через браузер.
5. Docker, CI, кэш, балансировщик, GraphQL, очереди, деплой.

С pz7 один и тот же сервис **tasks** (+ auth) идёт до pz16 — видно, как к одному коду добавляют инфраструктуру.

Порты 8081–8098 разнесены по практикам (pz3 — 8083, pz4 — 8084, pz5 редирект — 8085).

---

## Практика 1 — pz1-microservices

**Если спросят «что такое микросервис»:** отдельный процесс со своей зоной ответственности, свой порт, свой API.

- user-service — 8081, order-service — 8082.
- Заказ хранит `user_id`, полные данные пользователя берёт запросом в user-service.
- `/orders/{id}/full` — order-service собирает ответ из двух источников. Если user-service выключен — этот запрос не работает.
- Слои: обработчик → хранилище. Данные в памяти, без БД.
- Монолит проще отлаживать. Микросервисы проще менять и масштаировать по частям, но зависим от сети и порядка запуска.

---

## Практика 2 — pz2-grpc

**Если спросят «чем gRPC отличается от REST»:** контракт в `.proto`, бинарные сообщения, не JSON по HTTP.

- Порт **50051** — как в стандартных примерах gRPC; не HTTP, поэтому не 8080; не мешает pz1 (8081/8082) и остальным практикам.
- После изменения `.proto` — `generate.ps1`, появляются типы Go и заглушки.
- Ошибки — коды gRPC: NotFound, InvalidArgument, AlreadyExists (не HTTP 404/400).
- Локально без TLS. В реальной системе — шифрование, как в pz5.
- Удобен для вызовов между сервисами. Наружу для браузера чаще REST или GraphQL.

---

## Практика 3 — pz3-logging

**Если спросят «зачем структурные логи»:** по полям можно искать и фильтровать, не разбирая текст руками.

- Библиотека zap. В логе: метод, путь, код ответа, длительность, request_id.
- Промежуточный слой пишет один лог на HTTP-запрос.
- request_id в заголовке X-Request-ID и в каждой строке лога — связать запрос и лог.
- Логи в консоль и в файл одновременно.
- Уровни: отладка — детали, предупреждение — ошибка клиента, информация — успех.

---

## Практика 4 — pz4-monitoring

**Если спросят «логи или метрики»:** логи — про конкретный запрос; метрики — сколько запросов, какая задержка, сколько ошибок.

- Prometheus забирает данные с `/metrics`.
- Счётчик — сколько раз; гистограмма — время; датчик — значение «сейчас» (например, активные запросы).
- Путь `/students/1` в метриках записываем как `/students/{id}`, иначе слишком много разных меток.
- Grafana — графики по метрикам.

---

## Практика 5 — pz5-security

**Если спросят про безопасность API:** защита канала (HTTPS) и защита запросов к БД.

- HTTPS на 8443, с 8085 редирект на HTTPS.
- Запросы к PostgreSQL через подготовленные выражения (`$1`), id и email не вставляются в строку SQL.
- `/students/unsafe` — пример плохого кода для сравнения, в работе так не делают.
- Входные данные проверяем до БД (id, формат email).

---

## Практика 6 — pz6-web-security

**Если спросят про CSRF и XSS:**

- **CSRF** — чужой сайт отправляет форму от имени залогиненного пользователя. Защита: токен в форме, проверка на сервере при POST.
- **XSS** — в текст подставляют скрипт. Защита: шаблоны `html/template`, не склеивать HTML строками.
- Cookie: HttpOnly (скрипт не читает), SameSite=Lax, Secure на HTTPS.
- После успешного POST выдаём новый CSRF-токен — старый из формы не принимается.
- `/demo/unsafe` — намеренно небезопасный вывод для сравнения.

---

## Практика 7 — pz7-docker

**Если спросят «зачем Docker»:** одинаковое окружение, образ с приложением, запуск одной командой.

- Dockerfile в два этапа: сборка бинарника, в образ кладём только бинарник.
- docker-compose: auth (8087) и tasks (8088). tasks проверяет токен через auth.
- Настройки через переменные окружения, не IP в коде.
- `.dockerignore` — не копировать лишнее в образ.

---

## Практика 8 — pz8-ci-cd

**Если спросят «что такое CI»:** при отправке кода в репозиторий автоматически тесты и сборка.

- CI: `go test`, `go build`, сборка Docker-образов для auth и tasks.
- CD: публикация образа в реестр вручную, пароли только в секретах GitHub, не в репозитории.
- Образ помечаем хешем коммита — можно откатиться на точную версию.
- Есть вариант конвейера для GitLab — тот же смысл.

---

## Практика 9 — pz9-redis-cache

**Если спросят «как работает кэш»:**

- Redis — ускорение, источник правды — память/БД в сервисе.
- Схема: смотрим кэш → нет — читаем хранилище → пишем в кэш.
- У ключей время жизни (TTL), разброс времени (jitter), чтобы все ключи не истекли разом.
- При изменении и удалении задачи — сбрасываем кэш, иначе отдадим старое.
- Можно кэшировать ответ «не найдено», чтобы не дергать хранилище одним и тем же id.
- Redis недоступен — сервис работает без кэша, медленнее.

## Практика 10 — pz10-load-balancer

**Если спросят «зачем балансировщик»:** несколько копий одного сервиса, запросы распределяются.

- Три копии tasks (8091–8093), вход через NGINX на 8090.
- Распределение по кругу — по очереди на каждую копию. Заголовок X-Instance-ID — видно, какая копия ответила.
- `/health` — жива ли копия.
- Копии не должны хранить разное состояние в памяти. Иначе без «привязки клиента к серверу» данные разъедутся. Состояние — в Redis или БД.

---

## Практика 11 — pz11-graphql

**Если спросят «чем GraphQL отличается от REST»:** один адрес, клиент сам пишет, какие поля нужны в ответе.

- Схема в `schema.graphqls`, код генерирует gqlgen после `generate.ps1`.
- Песочница GraphQL на 8094 — проверка запросов в браузере.
- Изменения (мутации) — с Bearer-токеном, как в pz7.
- Бизнес-логика в сервисе и хранилище, GraphQL только вызывает её.

---

## Практика 12 — pz12-rest-graphql

**Если спросят «REST или GraphQL»:** оба на одних данных, порт 8095.

- REST `GET /v1/tasks` отдаёт все поля. GraphQL можно запросить только id, title, done — меньше лишних данных.
- REST для сложного экрана иногда — несколько запросов. GraphQL — один запрос, но сервер сложнее.
- REST: не найдено — 404. GraphQL: поле null и ошибки в теле ответа.
- REST проще кэшировать по URL. GraphQL обычно POST — кэш CDN так не работает.

---

## Практика 13 — pz13-rabbitmq

**Если спросят «зачем очередь»:** HTTP быстро отвечает, тяжёлую работу делает отдельный процесс потом.

- После создания задачи — сообщение в очередь `task_events`.
- Обработчик читает, обрабатывает, отправляет подтверждение. Без подтверждения сообщение снова в очереди.
- Очередь и сообщения с флагом сохранения — переживают перезапуск RabbitMQ (при правильной настройке).
- Предварительная выборка — сколько сообщений обработчик забирает заранее (у нас обычно 1).
- Это уведомление о событии, не гарантированная «задача на выполнение» — для этого pz14.

---

## Практика 14 — pz14-job-queue

**Если спросят про очередь задач с повторами:**

- `POST /v1/jobs/process-task` → ответ 202 «принято», не «готово».
- Очередь `task_jobs`, при ошибках повтор до 3 раз, потом очередь мёртвых писем `task_jobs_dlq`.
- `message_id` — повторное сообщение с тем же id не обрабатываем дважды (идемпотентность).
- `t_fail` — специальный id для проверки попадания в DLQ.
- Брокер доставляет «как минимум один раз» — потребитель должен быть готов к повтору.

---

## Практика 15 — pz15-vps-deploy

**Если спросят «как выложить на сервер»:**

- Собираем бинарник под Linux (`build-linux.ps1`).
- На VPS: бинарник в `/opt/tasks`, настройки в `/etc/tasks/tasks.env`, права на файл конфига 600.
- systemd: автозапуск, перезапуск при падении, отдельный пользователь tasksuser.
- Логи: `journalctl -u tasks`.
- Обновление: скопировать новый бинарник, `systemctl restart`. Откат — вернуть старый бинарник.

---

## Практика 16 — pz16-kubernetes

**Если спросят «чем Kubernetes отличается от systemd на одном сервере»:** управляет многими копиями в контейнерах, сам перезапускает, масштабирует.

- Deployment — сколько копий, обновление без простоя.
- Service — постоянный адрес к подам.
- ConfigMap — настройки без пересборки образа.
- Проверки liveness/readiness на `/health` — не слать трафик в мёртвую копию.
- Образ `techip-tasks:0.1`, для kind — загрузить образ в кластер.
- `kubectl scale` — больше копий; `port-forward` — доступ с ноутбука.

## Самое важное

1. **Микросервис и монолит** — монолит проще, микросервисы гибче по деплою, но сложнее из-за сети.

2. **Синхронно и асинхронно** (см. ниже).

3. **Логи и метрики** — лог про один запрос; метрики про поведение системы в целом.

4. **Безопасность** — шифрование, проверка входа, безопасный SQL, защита форм и cookie в браузере.

5. **Кэш** — ускоряет, но нужно сбрасывать при изменении и уметь работать без Redis.

6. **Docker и Kubernetes** — Docker упаковывает приложение; Kubernetes запускает и держит много таких упаковок.

### Синхронно и асинхронно — простыми словами

**Синхронно** — клиент отправил запрос и **ждёт ответа в том же соединении**. Пока сервер не ответил, для клиента операция не закончена.

Пример из pz1: `GET /orders/101/full` — order-service сам ходит в user-service и только потом отдаёт готовый JSON. Клиент ждал весь этот путь.

**Асинхронно** — клиенту **не нужно ждать**, пока тяжёлая работа доделается. Сервер быстро говорит «принял», а обработка идёт **в другом процессе**, часто через очередь.

Пример из pz14: `POST /v1/jobs/process-task` → ответ **202** «задача в очереди». Обработчик потом читает сообщение из RabbitMQ и обрабатывает. Клиент уже может закрыть запрос — результат будет позже (в логах обработчика или в другой системе).

| | Синхронно (HTTP сразу) | Асинхронно (очередь) |
|---|------------------------|----------------------|
| Клиент ждёт? | Да, до ответа | Нет, только подтверждение приёма |
| Где работа | В том же запросе | В обработчике / фоне |
| Если сервер упал посреди | Клиент видит ошибку | Сообщение может остаться в очереди и обработаться после перезапуска |
| Практики | pz1–pz12 (обычный API) | pz13–pz14 |

**pz13** — асинхронное **уведомление** («задача создана»). **pz14** — асинхронная **работа** с повторами и очередью для «битых» сообщений (DLQ).
